Zero-Downtime Hot Reloads vs Systemd Restarts

Why executing systemctl restart caddy is a dangerous anti-pattern on production servers, and how Caddy's in-memory configuration swapping guarantees zero dropped connections.

Official Upstream Reference: Upstream Caddy command-line reference on hot reloading and graceful shutdowns.
caddyserver.com/docs/command-line#caddy-reload ↗

☠️ The Danger of systemctl restart caddy

When an operator modifies a configuration file and executes: 

# ⚠️ DANGEROUS IN PRODUCTION
sudo systemctl restart caddy

Systemd sends SIGTERM or SIGKILL to Caddy's master PID. The entire operating system process terminates:

  • Socket Destruction: Port 80 and 443 listening sockets close immediately.
  • WebSocket Mass Disconnection: Every active clinic queue display, trading terminal, and chat app connection is abruptly severed.
  • Fleet-Wide Outage: If the new configuration has even a minor syntax error, Caddy fails to boot back up. Every subdomain on the server goes offline simultaneously.

✅ The Right Way: In-Memory Hot Reload

Always use Caddy's native reload command: 

caddy reload --config /etc/caddy/caddy.json

How Caddy Reload Works Under the Hood:

  1. Caddy reads /etc/caddy/caddy.json and validates the entire JSON schema in a temporary memory buffer.
  2. If the JSON is invalid, Caddy aborts the reload, outputs an exact error message, and keeps running the previous working configuration. Zero downtime!
  3. If valid, Caddy initializes the new handlers, binds any new upstreams, transfers the existing network listeners gracefully, and stops the old handlers.
  4. Active WebSockets and HTTP/2 multiplexed streams are preserved across the transition.

⚙️ The Caddy REST Admin API (Port 2019)

Alternatively, you can push configuration updates directly to Caddy's Admin API endpoint via HTTP: 

curl "http://localhost:2019/load" \
  -H "Content-Type: application/json" \
  -d @/etc/caddy/caddy.json

🛡️ Atomic Rollback Safety Built into Our Tools

Whenever caddy-subdomain, caddy-fileserver, or caddy-cli mutates /etc/caddy/caddy.json, it enforces a 3-step atomic transaction:

Step 1: Backup
Creates caddy.json.bak.<timestamp> before touching a single byte.
Step 2: Safe Reload
Writes new JSON and executes hot reload in memory.
Step 3: Auto-Revert
If reload fails, immediately restores the backup file and alerts the operator.
