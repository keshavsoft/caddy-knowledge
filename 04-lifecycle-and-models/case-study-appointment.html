Case Study: appointment-notifier

A step-by-step code investigation walkthrough of KeshavSoft’s real-world clinic queue calling application, proving how to inspect application source code and select the exact Caddy configuration.

Production Application Repository: Live clinic calling audio/visual display application.
github.com/keshavsoft/appointment-notifier ↗

🔬 The Code Investigation

When configuring Caddy for an existing application, never guess the routing requirements. Inspect the source code:

Step 1: Inspect Server Listener (`app.js`)

Looking at app.js in appointment-notifier: 

const server = http.createServer(app);
const wss = new WebSocketServer({ server });

server.listen(port, () => {
    console.log(`Server listening on port ${port}`);
});

Deduction: The HTTP server and WebSocket server share the exact same internal port (3000). There is no separate WebSocket port.

Step 2: Inspect Frontend WebSocket Connection (`display.js`)

Looking at client-side JavaScript in public/display.js: 

const protocol = window.location.protocol === 'https:' ? 'wss:' : 'ws:';
const socket = new WebSocket(`${protocol}//${window.location.host}/ws`);

Deduction: The frontend connects to standard port 443 via wss:// on the /ws path.

⚖️ Selecting the Template: Why `proxy` Over `ws-split`

Template Option Suitability Why
caddy-template proxy ✅ PERFECT MATCH HTTP and WebSockets share port 3000. Caddy automatically upgrades WebSocket connections on the single dial target.
caddy-template ws-split ❌ WRONG Requires a second listening port (e.g. 8080). Since appointment-notifier only has port 3000, routing /ws* to a non-existent port causes immediate 502 errors!

⚡ The Execution Command

npx caddy-template proxy appointment.keshavsoft.com 3000
