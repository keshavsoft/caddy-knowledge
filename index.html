The permanent, plain-English architectural reference for cloud ingress, automatic HTTPS, subdomains, reverse proxies, and static file servers on the KeshavSoft Ubuntu VPS fleet.

🧠 The Cold-Start Mental Model

Because reverse proxy and cloud ingress configurations are touched only once every few months, developers frequently suffer from cold-start amnesia:

  • "Did the connection fail because GoDaddy DNS hasn't propagated, or did Node.js crash?"
  • "Why did my Let's Encrypt certificate fail to issue?"
  • "Should I configure reverse_proxy to a port or file_server to /usr/share?"
  • "How do I add a new subdomain without breaking active client WebSockets?"

This knowledge base documents the exact conventions, tools, and JSON AST blueprints that power 103.174.102.116 so you can onboard new domains with 100% confidence.

🧭 The 3-Stage VPS Subdomain Maturity Model

Never configure DNS, Node.js ports, Caddy routes, and SSL simultaneously. KeshavSoft decouples hosting into three progressive verification stages:

Stage 1: Flight Check Zero Disk / Zero Code

Smoke Probe (static_response 200 OK)

Verifies that GoDaddy DNS reaches the server and Caddy provisions the Let's Encrypt certificate in memory. Does not touch disk folders or Node.js. 

npx caddy-subdomain probe call.keshavsoft.com
Stage 2: Static Server Real Disk I/O

Static File Server (/usr/share/...)

Provisions the Ubuntu directory, drops a responsive starter index.html, and configures Caddy's native file_server handler with auto-reload. 

npx caddy-fileserver init call.keshavsoft.com
Stage 3: Dynamic Application Full Backend Process

Reverse Proxy to Node.js / Docker

When the subdomain requires full server-side rendering or dynamic APIs, manage the process with ubuntu-service-cli and promote the Caddy route to forward traffic to the internal port (e.g. localhost:5000). 

npx caddy-subdomain add call.keshavsoft.com 5000

📦 The 4 Caddy Suite Repositories

Each repository in the suite has a single, strictly defined responsibility:

1. caddy-subdomain

The atomic subdomain engine. Injects Level-1 smoke probes, verifies live HTTPS handshakes, and seamlessly promotes to reverse proxies or static paths with automated backups.

Commands: probe • add • static • check • list

2. caddy-fileserver

The bridge between Caddy TLS (:443) and the Ubuntu filesystem. Automates /usr/share/<domain> provisioning, drops starter HTML/XML templates, and configures Caddy static routes.

Commands: init • check • template • list

3. caddy-template

The pure AST blueprint generator. Returns battle-tested, validated Caddy JSON route objects for unified proxies, split WebSocket ports, static file servers, and multi-domain aliases.

Templates: proxy • ws-split • static • multi-host

4. caddy-cli

The fleet orchestrator and inspection lens. Parses /etc/caddy/caddy.json, prints formatted port mapping tables, detects domain collisions, and safely appends routes.

Commands: inspect • -p (ports) • -d (domain) • add

🔍 Caddy JSON Route AST Anatomy

Every route inside apps.http.servers.srv0.routes follows a strict object hierarchy: 

{
  "match": [
    {
      "host": ["call.keshavsoft.com"]   // 1. SNI / Host header match
    }
  ],
  "handle": [
    {
      "handler": "subroute",            // 2. Encapsulates inner handler pipeline
      "routes": [
        {
          "handle": [
            {
              "handler": "vars",        // 3A. Sets the document root on disk
              "root": "/usr/share/call.keshavsoft.com"
            },
            {
              "handler": "file_server", // 3B. High-speed static file server
              "hide": ["/etc/caddy/Caddyfile"]
            }
          ]
        }
      ]
    }
  ],
  "terminal": true                      // 4. Stops evaluation once matched
}
Why terminal: true is mandatory: Without terminal: true, Caddy continues evaluating subsequent routes in the array, potentially causing fallback handlers to overwrite your HTTP response.

🛠️ Emergency Runbook & Gotchas

Issue 1: 502 Bad Gateway

Root Cause: Caddy received public traffic on port 443, but the backend process is not listening on the internal target port (e.g. localhost:3000).

Resolution: Use npx ubuntu-service-cli check <domain> to check if the systemd service is running, or verify with curl http://localhost:3000.

Issue 2: Hot-Reloading Without Dropping WebSockets

Never restart the Caddy service via systemctl restart caddy. A restart kills active client WebSockets and TCP tunnels. 

# The Safe Hot-Reload Command (Preserves all active TLS handshakes):
caddy reload --config /etc/caddy/caddy.json

Issue 3: Rolling Back Configuration

Every mutation performed by caddy-subdomain, caddy-fileserver, and caddy-cli automatically generates an atomic backup: /etc/caddy/caddy.json.bak.<timestamp>. 

# Restore from the latest backup:
cp /etc/caddy/caddy.json.bak.<timestamp> /etc/caddy/caddy.json
caddy reload --config /etc/caddy/caddy.json
