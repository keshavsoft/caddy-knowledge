Atomic Backups & Disaster Recovery

How every mutation performed by KeshavSoft tools guarantees atomic safety, and how to execute an instantaneous rollback if a configuration change fails.

🛡️ The Atomic Backup Guarantee

Whenever caddy-subdomain, caddy-fileserver, or caddy-cli modifies caddy.json, it enforces a non-negotiable safety check:

1. Read existing /etc/caddy/caddy.json
2. Write identical copy to /etc/caddy/caddy.json.bak.<timestamp>
3. Validate new route object and write to disk
4. Execute caddy reload --config /etc/caddy/caddy.json
5. If reload returns error → Immediately restore backup and trigger alarm

🚨 The 2-Second Emergency Rollback Procedure

If an operator manually edits caddy.json or needs to immediately revert to the last working state, run: 

# Restore the most recent timestamped backup:
LATEST_BAK=$(ls -t /etc/caddy/caddy.json.bak.* | head -1)
sudo cp "$LATEST_BAK" /etc/caddy/caddy.json
sudo caddy reload --config /etc/caddy/caddy.json
Zero Dropped Sockets
Because this executes via caddy reload rather than systemctl restart, rolling back restores the previous routes in memory without severing active WebSocket connections or dropping TLS listeners.
